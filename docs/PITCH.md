# Текст защиты SourceCraft Repo Health

Расчётная длительность: 5–6 минут без вопросов.

## Слайд 1. Решение

SourceCraft Repo Health отвечает на два вопроса: можно ли доверять репозиторию
сегодня и что нужно исправить в первую очередь. Сервис рассчитывает Repo Health
Score от 0 до 100, но не ограничивается одним числом: каждый балл связан с
метрикой, источником и подтверждающим фактом.

## Слайд 2. Проблема

Данные о здоровье проекта разбросаны по CI, issues, документации, активности и
AppSec. Их приходится собирать вручную, а зелёный pipeline или большое число
лайков сами по себе ничего не гарантируют. Пользователю нужна общая картина с
понятным приоритетом действий.

## Слайд 3. Архитектура

Backend на TypeScript и NestJS получает данные через SourceCraft API и CLI.
Шесть коллекторов анализируют отдельные категории. Scoring нормализует метрики.
BullMQ выполняет анализ асинхронно, а PostgreSQL хранит историю, evidence и
рекомендации. Ошибка одного источника не отменяет весь анализ.

## Слайд 4. Формула

В Score входят Security и Code Health с весом 20 процентов, остальные четыре
категории имеют вес 15 процентов. Если источник недоступен, его вес исключается
из знаменателя. Поэтому отсутствие данных не становится плохой оценкой. Data
Coverage отдельно показывает полноту исходных данных.

## Слайд 5. Объяснимость

Система различает четыре состояния: данные доступны, данных нет, доступ
запрещён, источник временно сломан. Для каждой доступной метрики сохраняются
исходное значение, нормализованный балл, вес, источник и evidence.

## Слайд 6. Пользовательский путь

В публичном рейтинге можно сортировать репозитории по Score, likes и активности.
Dashboard показывает категории, метрики, сильные и слабые стороны. После входа
через Я ID пользователь запускает первичный или повторный анализ и скачивает
Markdown или PDF отчёт.

## Слайд 7. Security

Техническое задание запрещает имитировать AppSec. Поэтому Security использует
только реальные findings команды SourceCraft CLI: SAST, SCA и secret scanning.
Если у PAT нет нужного разрешения, категория получает Permission Denied и не
штрафует Score. Сейчас именно так работает стенд для divkit/divkit.

## Слайд 8. Масштабирование

Тест крупного репозитория обрабатывает дерево из 10 500 файлов. API загружается
страницами по 500 файлов, общий кэш исключает повторные запросы, а очередь
позволяет добавлять worker-процессы независимо от веб-приложения.

## Слайд 9. Готовность

Проходят 73 автоматических теста, production-сборки и dependency audit без
известных уязвимостей. Docker Compose поднимает frontend, backend, PostgreSQL и
Redis. Внешними зависимостями остаются публичный домен и права токена AppSec.

## Слайд 10. Демонстрация

На демонстрации мы открываем рейтинг, переходим в Dashboard, раскрываем evidence,
запускаем повторный анализ и скачиваем отчёт. Главная ценность решения в том,
что пользователь получает не только оценку, но и следующий проверяемый шаг.

## Короткие ответы на вопросы

**Почему лайки не входят в основной Score?** Лайки отражают популярность, а не
качество инженерных практик. Они доступны как отдельная сортировка рейтинга.

**Что происходит при ошибке SourceCraft API?** Коллектор получает
`COLLECTION_ERROR`, его вес исключается, остальные категории продолжают расчёт.

**Почему Security иногда отсутствует?** Сервис не подменяет AppSec проверкой
файлов. Без реальных findings или прав доступа категория исключается.

**Как масштабировать сервис?** Увеличить число BullMQ workers, вынести PostgreSQL
и Redis в управляемые сервисы и ограничивать параллелизм запросов SourceCraft.
